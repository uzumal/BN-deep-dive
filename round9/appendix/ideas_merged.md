# 発想A（資産複利レンズ）13案

発想の共通原理: ゼロクリック検索69%・Google参照流入33%減の環境で「読み物」はAIに食われる。残るのはAIが引用せざるを得ない一次データ＝実測・私文書・実機検証・過去スナップショット。LLMにより「1700自治体のPDF」「数万の求人票」を個人が構造化・維持し続けることが史上初めて可能になった。

構造型: 型1観測所型(A1,A2) / 型2照合型(A3,A4) / 型3実測ツール排気型(A5,A6) / 型4互換・不具合ナレッジグラフ型(A7,A8) / 型5信頼監査・来歴型(A9,A10) / 型6公共記録の横断解放型(A11) / 型7手続き実例コモンズ型(A12,A13)

## A1. AI答弁公文書館（LLM Answer Archive）
- 一行: 数百の定点質問を全主要モデルに毎週投げ、回答を恒久保存する「AIの言ったこと」のWayback Machine
- 本体: 廃止モデルの回答は物理的に再取得不能（GPT-4の2023年3月版と6月版の挙動激変は arXiv:2307.09009 で実証済み）。時間経過そのものが模倣コストを無限大にする
- 母数: 直接訪問はAI研究者・記者・政策・GEO担当で月10^3〜10^4と小さい。引用・報道経由の間接到達とデータライセンス(B2B)が本体。「基準データ発行体型」
- なぜ今: モデル廃止サイクルが数ヶ月に短縮。企業向けブランド監視SaaS(LLM Pulse等)は乱立するが全て私有ダッシュボードで公共アーカイブが存在しない
- 発見経路: 事件駆動(モデル炎上時に唯一の証拠保有者として報道引用)／恒久DOI付きデータセット公開→学術引用／HN・GitHubオープンデータ公開
- 最近接: 学術LLMDrift(停止的)、reconnAIのLLM Changelog(リリースノート追跡のみ)、GEO監視SaaS群。差=回答本文の網羅的・公開・恒久アーカイブは無い
- 弱点自己申告: API実行コスト常時発生(月数万円規模)。収益化が遅くB2Bデータ販売頼み。質問セット選定の編集責任・中立性。ベンダー自身が公式アーカイブを出すリスク(ただし自社に不利な記録は出せない=第三者性が防壁)

## A2. 求人票タイムマシン（ゾンビ求人観測所）
- 一行: 企業採用ページとハローワーク公開データを毎日スナップショットし「掲載何日目か」「給与レンジがいつ下がったか」「出ては消える求人か」を記録する縦断台帳
- 本体: 消された求人票は再取得不能。掲載期間・再掲載回数・条件改定履歴という時間軸データは後発が追いつけない。求人×企業の名寄せグラフも蓄積
- 母数: 転職検討者は常時数百万人規模。現実的な月次利用は蓄積後10^4〜10^5。B2B(人材メディア・研究・エージェント)へのデータ提供が収益柱
- なぜ今: 空求人・おとり求人問題は周知だが定量記録が存在しない(追跡サイトは検索で確認できず)。LLMで雑多な採用ページの構造化抽出が個人でも回る
- 発見経路: 月次「ゾンビ求人ランキング」等を記者に定期提供／転職コミュニティで「この求人は通算487日掲載」の一次データとして貼られる／恒久URLの企業別ページ
- 最近接: OpenWork等口コミ(主観・企業単位)、Indeed等(現在形のみ履歴なし)。差=主観でなく機械的事実の縦断記録。v6 PricePulse と構造は似るが対象が紅海(価格)でなく空白(求人来歴)
- 弱点自己申告: 求人ポータルのスクレイピング規約違反リスク→企業直営ページ＋公的データ限定で網羅性が落ちる。削除要求・名誉毀損クレーム対応。「ブラック企業チェッカー」の既存文脈に回収される懸念

## A3. 見積もりのLevels.fyi（工事・修繕の明細行相場台帳）
- 一行: リフォーム等の見積書をアップすると明細行レベルで実勢分布と照合、匿名化データが「明細行単位の実勢価格台帳」に蓄積
- 本体: 見積書というWeb上に存在しない私文書のコーパス。AIの学習データに含まれず再生成不可能。明細行×地域×時期の分布は件数が増えるほど唯一無二に
- 母数: 住宅リフォーム年間約7兆円・数百万件。相見積もり文化。月次10^4〜10^5の閲覧が射程
- なぜ今: 「見積もりAIチェック」は2025年にlead-gen付帯機能として複数出現済み(Kirei One等)だが全て業者送客目的でデータ私有。「統計を全公開する中立台帳」は送客業者には構造的に真似できない。LLMで任意フォーマットの見積書抽出が可能に
- 発見経路: 診断結果ページ自体が共有物(「地域中央値の1.8倍でした」は怒りと実益で共有される)／消費生活センター・住宅系団体からの参照／年次「実勢価格白書」のメディア提供
- 最近接: lead-gen型診断、一括見積もりサイト。差=データを公開資産にする点と中立性。墓場v5「一回きり」への解決=利用者は一回でも資産はコーパス側に複利する(Levels.fyi構造)
- 弱点自己申告: コールドスタート(初期は照合先が薄い)。診断精度への責任。業界からの敵意。B2Bデータ販売先が限定的

## A4. 退去費用の公開台帳（原状回復Levels.fyi）
- 一行: 退去精算書を投稿すると国交省ガイドラインと地域実勢に照合して「ぼったくり度」判定、物件タイプ×築年×居住年数×請求額×交渉結果の公開実例DBが育つ
- 本体: 退去精算書という私文書コーパス＋交渉結果(減額幅)という結末データ。大家・管理会社別の請求傾向も長期で名寄せ資産に
- 母数: 引越し年間数百万件、退去費用トラブルは国民生活センター定番相談。「退去ガチャ」の語彙が既にある。月次10^4〜10^5射程
- なぜ今: 記事・相場解説は無数だが構造化された実例投稿DBは確認できず。読み物はAI検索に食われる側、実例分布データだけが残る側。精算書写真からの構造化抽出はLLMで初めて低コスト化
- 発見経路: 診断結果の共有動機(損得＋怒り)／退去は3〜4月集中で季節報道と相性良く毎年引用される／賃貸系YouTuber・司法書士等が参照する一次データ化
- 最近接: 国交省ガイドライン(規範のみ)、法律事務所の解説記事群。差=規範ではなく実勢の記録
- 弱点自己申告: 管理会社からの削除圧力・名誉毀損リスク(物件特定粒度の設計が生命線)。投稿の真正性検証(精算書写真必須だと摩擦、任意だと汚染)。A3と構造同一なので「2案で1案」と言われうる(その場合は本案A4を優先: 対象人口・感情強度・共有動機で勝る)

## A5. 内見ログ（部屋の実測カルテ＋実測マップ）
- 一行: 内見中に騒音dB・電波・採光・水圧・間取り実寸を1フローで記録するアプリ。個人の物件比較カルテとして単体で有用、匿名化実測値が「建物×時間帯の実測環境マップ」に蓄積
- 本体: 物理実測値はAIに生成できない。建物単位の夜間騒音・電波の実測分布はSUUMOにもGoogleにも存在しない。ツールが単体で便利だから「他人のための投稿」問題を回避=データは利用の排気ガス
- 母数: 賃貸内見は年間数百万人。アプリ初期DAU 10^3〜10^4、閲覧側(マップ)は蓄積後10^5射程
- なぜ今: 騒音計・メジャーアプリは単機能乱立だが内見統合＋地図資産化は確認できず。スマホセンサー精度とオンデバイスAI補正が実用域。不動産ポータルは大家側の利益相反でこのデータを絶対に作れない
- 発見経路: App Store/Playの「内見 チェック」検索獲得(新規ドメインSEO非依存)／賃貸系YouTuberの撮影定番ツール化(数十人への直接声かけ)／蓄積後は「駅別・夜間実測騒音」等がメディア素材
- 最近接: 単機能計測アプリ、マンションノート(主観口コミ)。差=主観でなく実測。v3棄却理由(完成形競合の薄いラッパー)はデータがどこにも存在しないため該当せず
- 弱点自己申告: スマホ測定の精度限界(相対比較として設計)。建物単位公開のプライバシー・大家クレーム。密度が出るまでマップは空(ツール単体価値で食いつなぐ期間が長い)

## A6. ワットログ（家電の実測電費・寿命の公開DB）
- 一行: スマートプラグ所有者の実測消費電力データ(機種×使用条件×実測kWh)を集約、「カタログ値ではない実測電気代」と経年劣化・故障時期を機種単位で公開
- 本体: 実測の時系列(新品時と5年後の消費電力差)は物理データで再生成不能。故障・寿命データは年数が経たないと絶対に作れない=先行者の時間差が堀
- 母数: 閲覧側は電気代高騰に関心を持つ全世帯(潜在10^6超)、投稿側はスマートプラグ所有者で現実には10^2〜10^3から
- なぜ今: 電気代高騰の常態化。実測はブログ単発記事のみで構造化DBは確認できず。SwitchBot等のAPIから半自動吸い上げ可能に。価格.comはメーカー関係上「公称値との乖離告発」を構造的にやれない
- 発見経路: ガジェットコミュニティのOSS的参加文化(計測好きは共有自体が動機)／「公称値と実測の乖離ランキング」は事件駆動報道と相性良い／電気代シーズンの定期引用
- 最近接: 価格.comレビュー(購入直後の主観のみ)、省エネ型録DB(公称値)。差=実測・経年。v1棄却理由(母数)に対し閲覧者は「電気代を気にする全員」で桁が3つ違う
- 弱点自己申告: 投稿者の裾野が狭くデータ密度に時間がかかる。測定条件の統制困難。メーカー反発。13案中最もコールドスタートが重い自覚

## A7. AIスタック互換グラフ（PCPartPicker for AI開発環境）
- 一行: 「このMCPサーバ×このクライアント×このモデル×このOSで動くか」の実機検証報告を構造化し、バージョン単位の互換・破損マトリクスとして公開
- 本体: 「動いた/壊れた」は実行した人間にしか分からない実機検証データ。エコシステムが速く動くほど鮮度維持がそのまま参入障壁(PCPartPickerの互換データと同型)。検証者の信頼グラフも蓄積
- 母数: AI開発ツール利用者はグローバル10^6超、公式MCPレジストリだけで9,652サーバ(2026年5月)。現実的月次10^4〜10^5
- なぜ今: 「MCP設定はツールごとにバラバラで断片化」が2026年の公然の悩み。既存は静的な個人製マトリクスが出始めた段階で、クラウド検証型の動的DBは空白
- 発見経路: READMEバッジ「verified with Claude Code vX / Cursor vY」(配布が製品に内蔵)／各ツールのDiscord/GitHub Issueで互換ページが貼られる／構造化データによりAIコーディングアシスタント自身が本DBを引用して答える
- 最近接: MCPディレクトリ群(Smithery等: 一覧のみで互換・破損情報なし)、各ツールのIssue(非構造)。差=横断・構造化・バージョン軸。v1と同型だが母数が「全AI開発者」
- 弱点自己申告: エコシステム標準化が進むと問題自体が縮む。公式レジストリが互換情報を持ち始めるリスク。検証報告の初期供給は自分で数百件作る覚悟が必要

## A8. アプデ信号機（更新「待て/行け」のクラウド実機DB）
- 一行: iOS/Android/Windows/主要アプリの各アップデートについて「機種×バージョンで問題が出た/出ない」を構造化収集、「あなたのiPhone 15でiOS 27.1は行けるか」を信号で答える
- 本体: 実機報告の蓄積と機種×バージョンの相性履歴(過去傾向は将来予測の資産)。個々の記事はAIが書けるが、手元の実機で何が起きたかの分布は集めた者しか持てない
- 母数: スマホ利用者ほぼ全員が潜在層(「iOS 不具合」は大型アプデごとに巨大検索需要)。現実的月次10^4〜10^5(日本語圏のみでも)
- なぜ今: 現状は解説記事メディアの独壇場=AIが再生成できる読み物でありAI検索に食われて消える側。構造化された実機報告DBは確認できず。OSアプデ頻度増とAI機能追加による不具合増
- 発見経路: 大型アプデ日という予測可能な事件駆動(当日に唯一の集計データを持つ者としてテック媒体が引用)／修理店・情シス・量販店の実務参照(B2B2C)／埋め込みウィジェット
- 最近接: Downdetector(障害検知であり更新不具合ではない)、記事型まとめ群。差=記事でなくDB、事後でなく意思決定支援(待て/行け)
- 弱点自己申告: 報告の質(思い込み・重複)のモデレーション負荷。公式改善で問題が減る長期リスク。「問題なし」報告を集める工夫が必要

## A9. MCP登記所（エージェント供給網の公開来歴台帳）
- 一行: 公開MCPサーバ/エージェントツールの「ツール定義・権限・挙動」を毎日スナップショットし、サイレント変更(rug-pull)を公開履歴として記録
- 本体: 過去のツール定義スナップショット。rug-pullは履歴がないと立証できず、履歴は事後には作れない。インシデント台帳と各サーバの「前科」ページが複利
- 母数: 開発者・セキュリティ担当で10^3〜10^4と小さいが、単価の高い層
- なぜ今: mcp-scanはSnykに買収され(2025年6月)私有の手元スキャン製品化。公開の・歴史を持つ・誰のものでもない台帳は空白。インシデントは増加中
- 発見経路: サイレント変更のadvisory公開がHN/セキュリティ媒体で回る／健全なサーバ作者が自らREADMEに「履歴クリーン」バッジを貼る／レジストリ各社へのフィード提供
- 最近接: Snyk Agent Scan(私有・手元スキャン)、学術MCP-Scanner。差=製品でなく公共記録。Certificate Transparency / HIBPの立ち位置
- 弱点自己申告: 母数が13案中最小で「広い層」要件に正面から反する(反論は「開発者インフラは母数でなく浸透で測る」)。Snyk/公式レジストリが公開履歴機能を出す可能性。誤検知時の加害リスク

## A10. レビュー信頼登記所（Fakespot亡き後の公開版）
- 一行: ECリスティングとレビュー群の状態を継続スナップショットし、不自然な変化(すり替え・大量削除・購入者層急変)を公開履歴として記録
- 本体: 過去のリスティング状態のアーカイブ(商品すり替え・水増しは履歴比較でしか立証できない)＋摘発事例台帳。判定アルゴリズムはコモディティでも5年分の状態履歴は再生成不能
- 母数: オンライン買い物客全員が潜在層(Fakespotは数百万ユーザー規模だった)。現実的初期は10^4
- なぜ今: Fakespotは2025年6〜7月に完全終了、AI生成レビュー氾濫で問題は悪化。日本ではステマ規制(2023年景表法)以降、行政・報道の基準データ需要
- 発見経路: やらせレビュー摘発報道のたびに履歴データ保有者として引用される／HIBP型の「このASIN/この店舗をチェック」恒久ページが掲示板で貼られる／消費者団体・研究者へのデータ提供
- 最近接: 正直に書く: Fakespot跡地には既にFakeFind・SureVett・RateBud等の小規模代替が乱立。ただし全て「今この瞬間の判定ツール(拡張)」で、縦断履歴の公開台帳は無い。差は「判定」ではなく「記録」
- 弱点自己申告: Amazonの敵意(スクレイピング法務リスク)。代替ツール乱立で「またこれか」と言われる筋が既にある。判定誤りが店舗への加害に。13案中で法務リスク最大

## A11. 施設カルテ（処分・事故・指導歴の横断台帳）
- 一行: 保育・介護・障害福祉・医療・飲食の施設について、行政処分・指導・事故報告(すべて公的公開情報)を横断で名寄せし「この施設の公的記録」を1ページで見られる台帳＋新規処分の通知
- 本体: 原データは公開されているが、こども家庭庁の事故DBはExcel配布、介護は都道府県ごと、飲食は保健所ごとにバラバラ。名寄せ・突合・継続更新という「維持労働」が資産。AIには再生成できても維持する主体がいない
- 母数: 保活世帯＋介護施設を探す家族＋外食客で年間数百万世帯が意思決定の瞬間を迎える。月次10^4〜10^5

- 母数: AI検索流入527%成長でサイト運営者の不安は普遍。世界数千万人のサイト所有者のうち月間数万〜十数万レポート実行の桁が狙い
- なぜ今: ゼロクリック93%時代の「自分は引用される側か」という新しい不安が2025-26年に発生したばかりで、無料・セルフサーブ・埋め込み型の回答が空白

- 最近接: Otterly.ai / peec.ai / Profound(エンタープライズ〜ミドル向け有料ダッシュボード。無料バッジ×公開ページの配布構造を持たない)。差=配布構造そのものと個人サイト層
- 弱点自己申告: 検出クエリのサンプリングに推論コストがかかりフリーミアム設計がシビア。「バッジは虚栄指標」批判。incumbentが無料枠を出せば圧殺されうる(データ蓄積の先行で守る)
