## 0.5. 設計原則の整理 — 「他社依存」の線引きを先に決める

依頼主の宣言「他社のソリューションを利用することを前提にした自社ソリューションはビジネスとして成立しない」は正しいが、**そのままでは何も作れない**（VPSもインターネットも他社である）。実務的な線引きは以下。

| 区分 | 定義 | 例 | 判定 |
|---|---|---|---|
| **代替可能なコモディティ基盤** | 明日ベンダを変えても同じデータが取れる | VPS、回線、S3互換ストレージ、Linux | **依存でない。使ってよい** |
| **観測対象** | 相手のToS違反にならない範囲で外から見るだけ。相手の協力不要 | 公開Webページ、公開API、DNS、BGP、CT log | **依存でない。これが本丸** |
| **データそのものの供給元** | 止められたら事業が消える | FlightRadar24 API、Numbeo API、Globalping API、SimilarWeb、他社のRUMデータ | **依存。ここに乗ってはいけない** |
| **無料枠に載せた本番** | 予告なく縮小される | Oracle Always Free（2026-06-15に半減 [A]）、Fly.io（無料枠廃止 [A]） | **依存。冗長化必須** |

→ **結論: 「自前のプローブ網から自分でデータを生成し、そのデータを自分のDBに貯める」までを自社で持てば原則は満たされる。VPSを借りることは違反ではない。** 逆に Globalping API や RIPE Atlas API を叩いてサービスを作るのは、たとえ無料でも原則違反である（後述A-5参照）。

### Cloudflare Workers を計測点にできるか — 結論と根拠

**結論: 「300拠点の計測網」としては使えない。HTTP到達性の補助的な観測点としてのみ使える。**

技術面 [A/B]:
- **ICMPは不可**。Workersランタイムに raw socket はない。ping / traceroute は原理的に実行不可。
- **TCPは `connect()` API で可能**（2023年導入）。ただし制約が多い:
  - **Cloudflare自身のIPレンジ宛の outbound TCP はブロック**されている（再開予定とされるが2026-08時点の状況は要確認）[B]
  - 接続確立前のソケットが約20〜21秒カウントされ続けるバグ報告あり → **タイムアウト系のスキャンで並列数が枯渇する**[B]
  - ヘッダ受信待ちの同時接続は6本まで
- **fetch() によるHTTP計測は可能**。ただしCloudflare内部での最適化が入るため「素のネットワーク遅延」ではない。
- **colo（実行拠点）を指定できない**。Smart Placementはむしろ「オリジンに近い場所で実行する」方向の最適化であり、計測とは逆。さらに**Freeプランのドメインは全データセンターに展開されない**（小規模PoPには載らない）[B]。→ **「330都市から測る」は実現できない。**
- Freeプラン: 100,000リクエスト/日、CPU 10ms/リクエスト [A]。

規約面 [B]:
- Cloudflare Self-Serve Subscription Agreement は **「VPNその他これに類するプロキシサービスの提供」を禁止**している。**Workersを他人向けの計測プロキシ／リクエスト中継として売る構成は、この条項に正面から当たる。**
- 旧2.8条（非HTML制限）はService-Specific Termsに移動し、Workersはnon-HTML配信可。ただし上記proxy禁止は残る。

→ **Workersの正しい使い道は「自分のRUM計測タグの受信エンドポイント（グローバルに低遅延で受ける）」であって、「送信側の計測プローブ」ではない。** ここは多くの人が誤解するポイント。

## A-3. 多リージョンのサーバーレス実行

| 方式 | 無料枠 | 超過後の実額 | 計測用途の評価 |
|---|---|---|---|
| **AWS Lambda** | 月100万リクエスト + 400,000 GB秒（Always Free、期限なし）[A] | $0.20/100万リクエスト + $0.0000166667/GB秒（x86）[A] | **1分間隔 × 20リージョン = 864,000呼び出し/月 → 無料枠内に収まる**[C]。128MB・500msなら 864,000 × 0.5s × 0.125GB = 54,000 GB秒 → これも無料枠内。**実質$0で20リージョン毎分HTTP計測が可能**。ただしICMP不可（VPC + raw socket制限）。IPは毎回変わる（AWSのIPレンジ内） |
| **Google Cloud Run** | 月200万リクエスト / 360,000 vCPU秒 / 180,000 GiB秒 [A] | 従量 | Lambda同様。コンテナなので実装自由度は高い |
| **Vercel Edge** | Hobbyプランは商用利用不可の規約 | — | **商用の計測基盤には使えない。除外推奨** |

**サーバーレス計測の本質的な限界**:
1. **ICMP/tracerouteができない** → ネットワーク経路の観測は不可能。HTTP/TCP/DNSのみ。
2. **IPが固定されない** → 「同じ観測点からの時系列」という計測の前提が壊れる。地域別価格差の検出などでは致命的。
3. **クラウドIPとして分類され、ブロックされやすい** → 到達性計測の結果が「相手のbot対策」に汚染される。
4. **リージョン数が限られる**（Lambda ≒ 30リージョン強、アフリカ・南米は薄い）。

→ **サーバーレスは「VPS網のバックアップ/クロスチェック」として持つのが正しい。主力にはならない。** ただし**コストが実質ゼロなので、持たない理由はない**。

### A-4-2. 合法性の色分け

| 手段 | 色 | 理由 |
|---|---|---|
| 自分の日本の回線から計測 | **白** | 問題なし |

### A-4-3. そもそも地域別価格差は存在するのか [B]

2025年の実測調査（18航空会社 × 47区間 × 6 VPNロケーション）では、**地理IPによる価格差が出たのはLufthansa / KLM / Swiss / Emiratesのみ、差分も為替マークアップ前で平均4.1%**という結果。

→ **「VPNで安く買える」という通説は、少なくとも航空券では大部分が誤り。** 地域価格差を売り物にする場合、**「差がある領域を先に特定する」ことが事業の中核**であり、そこが最も難しい。逆に言えば「差がない」ことを継続的に証明するデータにも価値がありうる（ただし買い手は薄い）。**むしろ差が確実に存在するのは、ソフトウェア/SaaS/ゲーム/ストリーミングのサブスク価格、Apple/Google のアプリ内課金、クラウド事業者のリージョン別料金**であり、これらは**認証不要の公開価格ページで観測できる → 居住者プロキシすら不要な場合が多い**。まずデータセンターIPで試すこと。

## A-5. 既存計測ネットワークへの参加

### A-5-1. RIPE Atlas — クレジット経済の実額 [A]

| 項目 | 数値 |
|---|---|
| プローブをホストして得られるクレジット | **15クレジット/分 = 21,600クレジット/日** |
| ping のコスト | **10クレジット / 結果1件** |
| traceroute のコスト | **既定30クレジット / 結果1件**（式: `10 × N × (int(S/1500)+1)`、N=パケット数既定3、S=パケットサイズ既定40オクテット） |
| DNS のコスト | 10クレジット / 結果 |
| TCP/SSL のコスト | 20クレジット / 結果 |
| HTTP のコスト | 40クレジット/結果という記述があるが**本セッションで確認できず [!]** |
| RIPE NCC会員の付与 | 100万クレジット/月 |
| 100万クレジット到達 | プローブ1台を挿しっぱなしで**約47日** |

**ソロにとっての意味を数字で出す [C]**:

```
プローブ1台ホスト = 21,600 クレジット/日
→ ping なら 2,160 結果/日
→ 「10プローブから15分間隔で1ターゲット」= 10 × 96 = 960結果/日 × 10 = 9,600クレジット/日

つまり、プローブを1台ホストして得られるクレジットで維持できるのは
「ターゲット2個を、10拠点から、15分間隔で ping する」程度。
traceroute にすると3倍のコストなので、ターゲット1個も維持できない。
```

→ **結論: RIPE Atlasのクレジットは「世界規模の常時監視」を賄う規模では全くない。** 「Tracerouteで全世界の障害を常時検知する」という構想をRIPE Atlasで実現するのは、クレジット経済上、数学的に不可能。

さらに致命的なのは **依存の問題**: RIPE Atlas API上に商用サービスを載せることは、依頼主の原則に真っ向から反する。RIPE NCCはAtlasの商用再販を歓迎していない。

**ただし価値がある使い方が2つある**:
1. **ソフトウェアプローブを自分のVPS全台に入れる** [A]。RIPE Atlasのソフトウェアプローブは VPS / Raspberry Pi / NUC にインストールでき、静的IPも必須ではない。**自前VPS 20台 = 20 × 21,600 = 432,000クレジット/日**が自動で貯まる。これは「自前網の副産物として得られる第二のデータソース」であり、健全。
2. **クロスバリデーション**。自前計測が「本当に世界の障害」なのか「自分のVPSだけの問題」なのかを、Atlasの独立した目で検証する。これは商用依存ではなく品質保証。

### A-5-2. NLNOG RING [A]

- **取引条件: サーバを1台寄贈すると、RING全体（500ノード超）にSSHアクセスできる。**
- 全ユーザーアクセスはSSH鍵管理。パスワードなし。**自分の寄贈機以外ではroot/sudo権限なし**。
- **これは驚異的なコスパ**: Vultr $3.50/月のVPS 1台の寄贈で、実質500拠点からの手動計測権を得る。

**ただし致命的な制約**: RINGは**ネットワークオペレータ間の相互デバッグ用コミュニティ**であり、**自動化された継続的計測や商用データ収集は文化的・規約的に想定されていない**。「500拠点を無料の計測網として使う」発想でRINGに入るのは、コミュニティに対する裏切りであり、追放される。**トラブルシュート時の人手の確認手段として持つのが正しい。**

### A-5-3. M-Lab [A/B]

- 40カ国100メトロに400サーバ超。**全データがオープン（BigQueryで無料クエリ可能）**、全ツールがオープンソース。
- NDT（速度計測）、Paris Traceroute等の生データがGoogle Cloud Storageに蓄積。
- **Host Managed Deployment Program** でサーバを追加できる。

→ **M-Labは「他社API」ではなく「パブリックドメインの計測データ」に近い。** 過去データの検証・自前データとの突き合わせには使える。ただし**M-Labデータを再配布するだけの事業は成立しない**（誰でも無料で同じものが取れる）。**自前のリアルタイムデータ × M-Labの歴史データ**という組み合わせなら差別化できる。

### A-5-4. Globalping (jsDelivr) [A] — 誘惑と罠

- ping / traceroute / dig / mtr / HTTP を**数千拠点から無料API**で実行できる。CLI、Slack app、GitHub botあり。
- プローブはDockerで誰でもホスト可（x86/ARM）。6台以上ホストすると寄贈者リストに掲載。$10/月以上のjsDelivrスポンサーはハードウェアプローブを受け取れる。
- 採用プローブを「adopt」するとクレジットが増える。

**罠**: Globalping APIを叩いてプロダクトを作るのは**最速で動くが、依頼主の原則に完全に反する**。jsDelivrが料金体系を変えた瞬間、レート制限を絞った瞬間に事業が死ぬ。**プローブをホストする側に回る（＝自前VPSにGlobalpingプローブも同居させる）のは無害でコミュニティ貢献になるが、事業のデータ源にしてはいけない。**

## A-6. 訪問者をプローブにする（RUM型）

### A-6-1. 先行事例の構造

| 事例 | 構造 |
|---|---|
| **Cedexis Radar（現 Citrix ITM）** [A] | コミュニティサイトに小さなJSタグを埋める → ページ読込完了後にタグが「起きて」、ITMに「何を測るか」を問い合わせる → 各CDN/クラウド上に置かれた小さな.gifを取得して到達性・レイテンシ・スループットを測る → テレメトリを送信。**数千サイトから1日数十億件のRUM**を収集し、そのデータでDNSベースのトラフィック分配（OpenMix）を駆動して収益化 |
| **Netflix fast.com** [A] | Netflix自身の本番Open Connect Appliance（OCA）に25MBの動画ファイルを置き、Rangeリクエストで1バイト〜25MBを取得して速度を測る。**「他人のサーバ」を一切使わず、自社CDNを計測ターゲットにした**点が本質。ダウンロードのみを測ると割り切った |
| **Cloudflare speed.cloudflare.com / Radar Internet Quality** [A] | 自社エッジ（180都市超）を計測ターゲットに。**speed.cloudflare.comの結果とベンチマークデータを集約**し、国別・AS別の帯域・レイテンシ・ジッタをRadarで公開。ASNごとに推定ユーザー人口で加重してバイアスを補正している |

**3つに共通する構造**: **計測ターゲットが自社インフラである。** 訪問者のブラウザは「クライアント」であって、他人のサーバを叩かせているわけではない。ここが法的・倫理的に決定的に重要。

### A-6-2. ブラウザから実際に何が測れるか [A]

| 手段 | 取れるもの | 制約 |
|---|---|---|
| **Navigation Timing / Resource Timing API** | DNS解決時間、TCP接続時間、TLSハンドシェイク、TTFB、転送時間 | **クロスオリジンのリソースは大半のフィールドが0または空文字になる。`Timing-Allow-Origin` レスポンスヘッダを相手が付けていない限り、詳細は取れない** → **他人のサイトの内訳は測れない。自分が制御するエンドポイントなら全部取れる** |
| **fetch() の手計測** | 総所要時間、成否、ステータス | CORSに阻まれる。opaque responseでも「時間」だけは測れる（成否は曖昧） |
| **WebRTC** | 従来はローカルIPが取れたが、**Chrome/Edge/Firefox/Safariがすべて mDNS ホスト名に難読化済み**（Chrome M73〜） | **ローカルIP収集は事実上死んでいる**。STUN経由のパブリックIP取得は依然可能 |
| **Network Information API (`navigator.connection`)** | effectiveType（4g等）、downlink、rtt | **W3Cでの仕様策定は中止済み。「参照・実装の基礎にすべきでない」とされている**。Chrome系でのみ動く。Safari/Firefox非対応 |
| **画像/ビーコンのタイミング計測（Cedexis方式）** | 任意ホストへの到達性・大まかなレイテンシ・スループット | 自分でターゲットを世界に置く必要がある → **結局A-1のVPS網が必要**。RUMはVPS網の「代替」ではなく「増幅器」 |

### A-6-3. 法規制 — 日本ではここが直撃する

**改正電気通信事業法 27条の12「外部送信規律」（2023-06-16施行）** [A]:
- **登録・届出の有無にかかわらず、ウェブサイト運営者／アプリ提供者に広く適用される。**
- 利用者の端末から利用者に関する情報を外部（第三者のサーバ等）に送信させる場合、**送信される情報の内容・送信先・利用目的の「通知または容易に知り得る状態への公表」が必要**。
- 利用者の**同意を得ている場合は事前通知・公表は不要**だが、同意取得にあたっても事前の通知・公表が望ましいとされる。

→ **RUM型計測タグを他社サイトに配布する = まさにこの規律の直撃対象。** 「あなたのサイトに貼るだけでOK」というセールストークは日本では通らない。**タグ配布者は、タグを貼る各サイト運営者に対して「何を外部送信するか」の開示文面を提供する義務が事実上発生する。**

**GDPR / ePrivacy**:
- IPアドレスは個人データ [B]。
- RUM計測は「サービス提供に厳密に必要」とは言い難く、**EU圏訪問者については同意（consent）が必要になる可能性が高い**。同意率は実務上30〜60%程度に落ちる → **EU圏のデータ品質が構造的に劣化する**。

**通信の秘密（電気通信事業法4条）** [B]:
- 罰則は法179条。
- 「登録・届出が不要な電気通信事業」を第三号事業といい、**届出不要でも電気通信事業に該当すれば通信の秘密の規律は及ぶ**という整理。
- 計測サービスが電気通信事業に該当するかは事業設計次第（クローズドなチャット/会議機能があれば登録・届出が必要になる、という総務省整理がある）。**単なる自社計測データの公開は該当しにくいが、他者の通信を中継・保存する設計にすると一気に該当リスクが上がる。**

### A-6-4. 鶏卵問題 — フォロワーゼロからどう始めるか

**構造**: RUMは「訪問者がいる → データが取れる → データに価値が出る → 人が来る」の循環。**入口の訪問者ゼロが最大の障壁で、これは技術では解決できない。**

Cedexisは「CDN選定に困っている企業」に**先にトラフィック分配の価値を提供**し、その対価としてタグを貼らせた。Netflixは**既に数億の視聴者を持っていた**。Cloudflareは**既に全Web20%超の前に立っていた**。**3つとも「先に別の資産があった」。純粋な鶏卵突破の成功例ではない。**

ソロが現実的に取れる打ち手（優先順）:
1. **RUMを主力にしない。** 自前VPS網（A-1）でデータを作り、RUMは後から「精度を上げる第二層」として足す。**これが唯一の現実解。**
2. **無料で価値のあるツールを先に出す**（例: 「あなたのサイトを世界20拠点から測る」の無料版）。ツール利用者自身が計測トリガーになる = **訪問者がそのままプローブになる自己充足設計**。Globalpingやspeed.cloudflare.comが実質これ。
3. **OSSのライブラリ/SDKにタグを埋める**のは**やってはいけない**（Coinhive的な同意なき実行になり、外部送信規律にも抵触）。

## B-1. ポートスキャンの法的位置づけ

### 日本 — 不正アクセス禁止法 [A]

- **ポートスキャン自体は不正アクセス禁止法違反に当たらないのが通説。** 同法の「不正アクセス行為」は3類型（他人の識別符号の入力／セキュリティホール攻撃）に限定され、**ポートスキャンはそのいずれにも該当しない**。
- **かつ、同法には未遂罪・予備罪の規定がない。** よって「侵入の準備行為」としても処罰されない。
- **しかし**: 弁護士解説は一様に「攻撃の前兆と見なされトラブルになりやすいので控えるべき」と述べる。**大量・高頻度なら偽計業務妨害（刑法233条）が別途成立しうる**。

### 岡崎市立中央図書館事件（Librahack事件、2010年）[A] — 日本で最も重要な前例

- 中川圭右氏が、図書館の新着本ページに**1秒に1回、1日1時間**アクセスするプログラムを実行。
- **偽計業務妨害容疑で逮捕、21日間勾留、6月14日に不起訴処分。**
- **後の検証で、原因はスクレイピングではなく三菱電機インフォメーションシステムズ製システムの欠陥だったことが判明。**
- **1秒1回はIT実務上「常識的な間隔」であり、それでも逮捕された。**

**この事件から引き出すべき教訓は3つ**:
1. **日本では「技術的に正しい」ことが法的安全を保証しない。** 相手のシステムが脆弱なら、こちらの善意も頻度の妥当性も関係なく刑事事件になりうる。
2. **相手が公的機関・非営利機関の場合、特に危険。** 「業務妨害された」と申告する動機と窓口がある。
3. **1秒1回でも危ない = 商用スクレイピングの安全な頻度は、日本の相手に対しては桁違いに保守的であるべき**（数分〜数時間間隔）。

### 米国 — Shodan / Censys は何を根拠に合法にやっているか [A/B]

明文の許可があるわけではない。**以下の運用の積み重ねで「訴えられない位置」を維持している**:

1. **CFAAは「認証の突破（without authorization）」を要件とする。** ポートに接続してバナーを読むだけでは認証を突破していない。**Van Buren v. United States (2021, 最高裁)** がCFAAの適用範囲を狭く解釈したことも追い風。
2. **オプトアウト機構を公開している。** Censysは自社のスキャン用サブネット/ASN（例: 66.132.159.0/24、66.132.148.0/24 等）を公開し、**「これらをブロックすれば日次スナップショットから自動的に除外される」**と明言。ただし**過去データは削除されない**。
3. **エクスプロイトを一切行わない。** 接続してバナーを取るのみ。脆弱性の実証（PoC実行）はしない。
4. **ZMap Scanning Best Practices [A]** の遵守: 必要以上に大きく・頻繁にスキャンしない／目的に必要な最小レートで行う／除外要求の窓口を用意する／スキャン元IPレンジを公表して運用者が自分で落とせるようにする／逆引きDNSにスキャン目的を書く／発見した脆弱性は責任ある開示を行う。
5. **Menlo Report（米国土安全保障省 科学技術局、2012-08-03公表）[A]** の倫理枠組みに沿っていると主張できる形にしている。

**ソロへの含意**: これらはすべて**「研究者・大学・資金力のある企業」の装備**である。オプトアウト窓口の運用、abuse対応、逆引きDNSの整備、責任ある開示の実務 — **ソロがこれを回すのは非現実的。かつ、そもそもVPSのAUPが先に効いて事業が止まる（C章）。**

**→ ポートスキャンを事業の中核に据えるのは、ソロにとって最悪の選択。この道は閉じている。**

| **EU** | **Ryanair v. PR Aviation (CJEU, 2015)**: データベース権・著作権の対象外のデータベースについては、**契約（利用規約）による制限は有効**。→ **EUは米国と逆の結論になりうる。ToSが効く。** |
| **日本** | 著作権法**30条の4**（情報解析目的の利用は原則適法）[A]。ただし**ただし書**: 「著作権者の利益を不当に害する場合」は除外。**取得したデータをそのまま再掲載することは不可。統計化または非類似レベルへの加工が必須**。<br>加えて**不正競争防止法の「限定提供データ」**、**著作権法のリーチサイト規制**、そして**岡崎図書館事件が示す偽計業務妨害**。 |

### 実務上の壁 — 2026年のCloudflareが最大の障害 [A/B]

- **Cloudflareは全Webトラフィックの20%超の前に立つ。**
- **2025-07-01: Pay Per Crawl 開始**（クローラがページを取得するたびに課金する仕組み）。
- **2026-07-01: モデル変更。「クロールごとの課金」では不十分として、「回答に content が実際に登場したときに publisher に払う」方式を提案。**
- **2026-09-15から、Training / Agent に分類されたクローラを、広告を表示するページ上でデフォルトブロック。新規顧客・既存顧客の新規サイト・そして既存の全Freeプラン顧客に適用。** Search 分類は許可のまま。
- **AI関連クローラは2026年6月時点で全クローラリクエストの52%**（2025年春の22%から急増）。
- **1日10億件超の402（Payment Required）レスポンス**を返している。

→ **「自分でクロールする」の難易度は2025→2026で劇的に上がった。** 2026-09-15以降、**Cloudflare配下のサイトはデフォルトで自動クロールを拒否する方向**であり、**フリーの個人サイトほど対策が入る**（既存Free顧客にも適用されるため）。

**ソロが取るべき現実的な戦略**:
1. **Cloudflare配下でないターゲットを選ぶ。** 各国政府サイト、公的統計、大手ECの一部、API公開されているサービス。
2. **公式APIがあるなら、規約の範囲でAPIを使う**（これは「他社依存」だが、価格ページのHTMLをパースするより遥かに安定し、規約違反にもならない）。
3. **User-Agentを正直に名乗り、連絡先URLを入れ、robots.txtを尊重し、頻度を極端に落とす。** 「1日1回」なら大半のサイトで問題にならず、ブロックもされにくい。**「毎分」を欲しがるとすべてが壊れる。**
4. **ヘッドレスブラウザ + 居住者プロキシで力づくで抜く道は、コスト・法務・持続性のすべてで悪手。** これは Bright Data 等の資本力ある事業者の土俵。

## B-3. 画像・映像の自動解析

| 論点 | 日本での整理 |
|---|---|
| **著作権** | **30条の4により、情報解析目的での複製・解析は原則適法**[A]。画像から特徴量を抽出する行為はここに入る。**ただし元画像をそのまま再掲載・再配布することは不可。** ただし書（権利者の利益を不当に害する場合）にも注意 |
| **肖像権・プライバシー** | **個人情報保護法の遵守だけでは不十分。** 肖像権・プライバシーは私法上も保護され、**損害賠償請求と差止請求の対象**になる[A] |
| **ガイドライン** | **「カメラ画像利活用ガイドブック ver3.0」（2022年3月、IoT推進コンソーシアム／総務省／経済産業省）**[A]。令和2年・令和3年の個人情報保護法改正に対応。**顔識別機能については別途「犯罪予防や安全確保のための顔識別機能付きカメラシステムの利用について」（2023-03-30公表）**あり |

**ソロ向けの結論**:
- **人が写り込まない対象に限定すれば、リスクは劇的に下がる。** 例: 商品画像、駐車場の空き台数、建設現場の進捗、船舶・航空機、農作物、看板の価格表示、混雑度（人数カウントのみで個人特定しない）。
- **顔・車両ナンバーが写る解析には手を出さない。** 収益に対してリスクが釣り合わない。
- **公開ライブカメラの映像を継続的に取得して解析するのは、著作権的には30条の4で通せる可能性が高いが、カメラ設置者のToS・帯域負荷・肖像権の三重リスク**。個別に許諾を取れる相手を選ぶ方が結局早い。

## B-4. BGP / CT / WHOIS の自前受信

### BGP [A/B]

| 方式 | コスト | 評価 |
|---|---|---|
| **RIPE RIS Live（WebSocket JSON API）+ RouteViews + MRTアーカイブ** | **無料** | データはパブリックドメイン。**「他社API依存」の懸念は薄い**（RIRの公共サービスであり、RIPE/Univ. of Oregonの両方が独立に提供 = 単一障害点でない）。`https://data.ris.ripe.net/` からMRTを直接ダウンロード可 |
| **bgp.tools のルートコレクタにピアする** | 自ASN + BGP4スピーカ + PeeringDBアカウントが必要 | データを「もらう」のではなく「提供する」側。自ASNを持っている人向け |
| **自前ASN取得 + 自前コレクタ** | **RIPE: LIR会員 €1,800/年 + 初回€1,000。スポンサリングLIR経由なら €50〜150/年**。**ARIN: 会員不要、ASN $250/年 + Registration Services Plan**。AFRINICが最安（ASN維持費なし） | **加えて /24 IPv4 または /48 IPv6 の保有、ROA設定、IXポート費用、トランジット費用が必要。ソロには過剰投資。** |

→ **BGPは自前受信しない。RIS Live + RouteViews の無料フィードで十分。** ここは「自前主義」を貫くべき領域ではない（データが完全にパブリックで、誰かに止められる性質のものではないため）。

### CT（Certificate Transparency）[A/B] — 過小評価されている領域

- **Chrome Root Program Policy により、2026-06-15までに全CAが全TLS precertificate/certificate を最低1つのCTログに記録することが義務化。** → **事実上、世界中の証明書発行が全部見える。**
- ログは**Static CT API（タイル方式）** に移行しており、**従来の `get-entries` より高速・安価に取得できる設計**。
- **自前でCTモニタを回すことは技術的に完全に可能。** RFC 6962 / Static CT API に従ってログをダウンロードし、自分のDBに入れるだけ。**誰の許可も要らず、誰にも止められない。**

**ソロにとっての意味**: **「他社に依存せず、世界規模のデータを、合法的に、低コストで、リアルタイムに得られる」という条件を、CTはほぼ完璧に満たす数少ない領域。**
- 新規ドメインの出現、企業のインフラ変更、フィッシングドメインの発生、特定業界のサービスローンチ、M&Aの兆候（証明書のOrganization変更）——すべて証明書から見える。
- 課題は**データ量**（全ログを追うとTB級）。**ドメイン名だけを抽出して保存すれば桁が2つ落ちる**[C]。CX22（€3.79/月）1台 + オブジェクトストレージで回せる規模。
- 競合: crt.sh、Cloudflare CT Monitoring（2026-08にGA）、Censys。**「全部を見る」では勝てないが、「特定業界に絞って意味づけする」なら勝てる。**

### WHOIS / RDAP / ゾーンファイル [A/B]

- **RDAP**: IANAのbootstrapから各RIR/レジストラのRDAPサーバに直接問い合わせ可。無料。レート制限あり。
- **ICANN CZDS**（`https://czds.icann.org/`）: gTLDのゾーンファイルを**無料**で取得できる公式ポータル。**.com / .net / .name を含むVerisign運営gTLDもCZDS経由で提供**[B]。
  - **ゾーンファイルは24時間ごと更新（00:00〜06:00 UTC に配布）**[B]。
  - **申請は「正当な企業または学術機関を代表していること」と「合法かつ倫理的な利用目的」が要件**[B]。**個人事業主が通るかはTLDごとの判断**で、**全ゾーンの承認完了まで1ヶ月以上かかることがある**[B]。
  - **2026年の新gTLDラウンドに合わせてCZDS 2.0 に刷新**[B]。
- → **申請は無料なので、今日出しておくべき。承認に1ヶ月かかるなら、着手が早いほど得。**

## B-5. スループット計測

- **帯域コストが直接効く唯一の計測。** 最安VPSは0.5〜1TB/月。1回10MBのダウンロード計測を**20拠点 × 毎分** で回すと `20 × 1440 × 10MB = 288GB/日` → **月8.6TB。1拠点あたり月432GB。** 最安プランの上限を即座に超える[C]。
- **現実的な設計**: 頻度を **1時間に1回**に落とし、サイズを **1〜5MB** にする → `20 × 24 × 5MB = 2.4GB/日 = 月72GB` → **1拠点あたり月3.6GB。余裕で収まる**[C]。
- **fast.com の教訓**: ダウンロードのみに絞り、自社の本番サーバをターゲットにした。**アップロード計測は帯域が倍かかる上、価値が低い。**

# C. 合法性・持続可能性の壁

## C-1. 能動計測はどこから問題になるか

**閾値は法律ではなくAUP（利用規約）で先に来る。** これが最重要の実務的発見。

| プロバイダ | AUPの文言（要旨） | 実際の運用 |
|---|---|---|
| **Vultr** | 「ネットワークプロービングまたはポートスキャンツールは、**宛先ホストおよび/またはネットワークから明示的に許可されている場合のみ**許容される。**許可のないポートスキャンは、いかなる理由であれ厳格に禁止**」[A] | — |
| **DigitalOcean** | 「DigitalOceanのシステム/ネットワークに対するプローブ、スキャン、侵入、脆弱性テストの試み、または**DigitalOceanの事前の書面による同意なしに本サービス上/本サービスを用いたセキュリティ調査・マルウェア調査を行うこと**は禁止」[A] | — |
| **Hetzner** | ポートスキャン / Torrent / IRC / Tor Exit Node は**全ロケーションで禁止**[B] | **最も強硬。「スキャン開始から1〜2時間でサスペンド」の報告あり。abuse通知後の猶予は重大度により6〜48時間、ポートスキャンは約6時間**[B] |
| **OVH** | 「ペンテストに寛容なToS」との評価（$4.20/月）[B] | **要一次確認。この一点で選ぶのは危険** |

**abuse報告によるVPS停止の実態** [B]:
- Hetznerはスキャン検知が積極的で、**数時間でサスペンド**。
- OVHは**abuse問題が継続すると、サービスを恒久的にオフラインにしアカウントを閉鎖**した実例あり。
- 「大手ホストではabuseによるサスペンドを防ぐ方法はない」というのがコミュニティの総意。

**→ 実務的な結論: ICMP ping と HTTP GET は事実上どこでも問題にならない。ポートスキャンは事業として成立しない。この線を絶対に越えないこと。**

## C-2. 頻度の設計 — 実務的な安全域 [C]

| 計測 | 単一ターゲットへの安全な頻度 | 根拠 |
|---|---|---|
| ICMP ping | **毎分〜10秒間隔** でも通常問題なし | 帯域も負荷も無視できる |
| TCP接続（既知ポート1本） | **毎分** | 常時監視サービス（UptimeRobot等）が普通にやっている水準 |
| HTTP GET（トップページ・軽量エンドポイント） | **毎分**（大手サイト）／**5〜15分**（中小サイト）／**1日1回**（公的機関・非営利） | 岡崎事件を踏まえ、日本の公的機関には極端に保守的に |
| Webページの本文取得（数十〜数千ページ） | **1〜数秒に1リクエスト、かつ深夜帯、かつ1日1周** | 岡崎事件が「1秒1回」で逮捕された事実を直視する |
| traceroute | **5〜15分間隔** | 中間ネットワークに負荷をかけるため |
| スループット | **1時間に1回** | 帯域コスト |
| ポートスキャン | **やらない** | AUPで即死 |

## C-3. 日本法のチェックリスト

| 法令 | 該当場面 | ソロが取るべき対応 |
|---|---|---|
| **不正アクセス禁止法** | ID/パスワードを使う、認証を回避する、脆弱性を突く | **絶対に認証の向こう側に行かない。** 未遂・予備の処罰規定がないのでポートスキャン自体は不該当だが、AUPで死ぬ |
| **刑法233条 偽計業務妨害** | 高頻度アクセス、相手システムのダウン | **岡崎事件の教訓。1秒1回でも逮捕されうる。日本の相手には極端に保守的に。連絡先を明示したUAを必ず名乗る** |
| **著作権法30条の4** | 取得データの解析 | **解析はOK。生データの再掲載はNG。統計化・非類似化して出す** |
| **著作権法（リーチサイト規制）** | 侵害コンテンツへのリンク集約 | 該当しない設計にする |
| **不正競争防止法（限定提供データ）** | 有償・限定提供されているデータの取得 | **ログインの向こう側・有料の向こう側には行かない** |
| **電気通信事業法4条（通信の秘密）** | 他者の通信を中継・保存する設計 | **他人の通信を運ばない設計にする。** 自分のプローブが自分で生成したトラフィックのみを扱えば該当しにくい |
| **電気通信事業法27条の12（外部送信規律、2023-06-16施行）** | **訪問者のブラウザから外部に情報を送信させる = RUM型** | **通知・公表または同意が必須。タグ配布ビジネスは日本ではこれが必須要件になる** |
| **個人情報保護法 + カメラ画像利活用ガイドブックver3.0** | 画像・映像解析 | **人が写らない対象に限定する** |

## C-4. 「持続可能性」の観点で最も危険なもの（危険順）

1. **無料枠に本番を載せる** — Oracleが2026-06-15に予告なく半減（8/18に超過分削除）、Fly.ioが無料枠廃止。**実証済みのリスク。**
2. **単一VPSベンダに全拠点を置く** — abuse報告1本で全滅。
3. **他社API（Globalping、RIPE Atlas、FlightRadar24等）をデータ源にする** — 依頼主の原則そのもの。
4. **ポートスキャンを核にする** — AUPで数時間で止まる。
5. **RUM型を主力にする** — 鶏卵問題 + 外部送信規律 + GDPR同意。
6. **Cloudflare配下のサイトを高頻度でクロールする** — 2026-09-15以降デフォルトブロック方向。

| **合計** | **≒ $125.40/月** | **実拠点31（22カ国以上） + 疑似8 = 39観測点** |

**実行できること** [C]:
- **ICMP ping**: 31拠点 × **3,000ターゲット × 毎分** = 134M レコード/日
- **HTTP**: 31拠点 × **2,000ターゲット × 毎分**
- **traceroute**: **1,000ターゲット × 5分間隔**
- **DNS**: **10,000ドメイン × 5分間隔**、国別リゾルバ差分の完全観測
- **TLS**: 50,000ドメイン × 日次
- **スループット**: 31拠点 × 5MB × 毎時 = 各拠点3.6GB/月（帯域枠内）
- **CTログ**: 全ログのドメイン抽出をリアルタイム
- **データ量**: 圧縮後 **4〜8GB/日**[C]。**この規模では、生データの保持期間を7〜30日に切り、以降は1分→5分→1時間の階層ダウンサンプリングが必須。** ClickHouse + R2で階層化。**ここを設計せずに始めると、3ヶ月でストレージが破綻する。**
- RIPE Atlasクレジット: 31 × 21,600 = **669,600/日**

**帯域の注意 [C]**: 31拠点 × 各0.5〜1TB = 合計15〜31TB/月の枠。純計測（ping/HTTPヘッダ）なら1拠点月数GB。**スループット計測とページ本文取得だけが帯域を食う。ここを制御すれば枠は問題にならない。**

# 2. ソロが世界規模の計測を持つための最良構成 トップ3

## 【1位】Vultr主軸のVPSプローブ網 + サーバーレス無料層 + 自前CTモニタ

**構成**: D-2（月$37）で始めてD-3（月$125）へ拡張。

**なぜ1位か**:
- **完全に自前。** データの生成から保存まで他社APIが1つも介在しない。依頼主の原則を100%満たす。
- **Vultr 32DC/19カ国が、$3.50/拠点という単価で地理的多様性を単独で提供する。** 他に代替がない。
- **ICMP + HTTP + DNS + TLS のみに絞れば、AUP違反にも法的リスクにも触れない。** ポートスキャンをやらない限り、この構成は「怒られない」。
- **AWS Lambda / Cloud Run の無料枠が実質$0でクロスチェック層を提供する**（無料枠に依存しているが、消えても本体は死なない = 正しい無料枠の使い方）。
- **自前CTモニタが「ネットワーク以外の世界規模データ」を同じインフラで供給する。** 依頼主の「ネットワークに限らない」という方針に直結。

**弱点**: Vultrへの集中。→ **Contabo/Hetzner/RackNerdで3社に分散する設計をD-3で入れてある。**

## 【2位】APIの挙動観測に特化した計測網（LLM/決済/クラウドAPIの世界別レイテンシ・可用性・挙動変化）

**構成**: D-2の拠点網をそのまま使い、**計測対象を「自分が正規に契約したAPI」に限定する。**

**なぜこれが強いか**:
- **法的リスクが構造的にほぼゼロ。** 自分が契約者として自分のキーで自分のリクエストを送るだけ。不正アクセスでもスクレイピングでもない。robots.txtもWAFも関係ない。**Cloudflareの2026-09-15ブロックの影響を一切受けない。**
- **拠点を持つことが直接的に価値になる領域。** LLM API、決済API、地図API、クラウドのコントロールプレーン — これらは**リージョンによってレイテンシ・レート制限・実際に返るモデル/挙動が違う**。この差分データは誰も体系的に持っていない。
- **「壊れたこと」が即座に価値になる。** APIの応答遅延、レスポンス形式の非互換変更、モデルの静かな差し替え、レート制限の変更 — 開発者が最も知りたい情報であり、現に検知手段がない。
- **ソロの元Cisco SE + Webエンジニアという経歴が、そのまま説得力になる**（フォロワーゼロの状態で「なぜこの人のデータを信じるのか」に答えられる）。
- **データ量が小さい。** 数百APIエンドポイント × 31拠点 × 毎分 でも、ping網より遥かに軽い。

**注意点**: **APIのToSでベンチマーク結果の公表を禁止している事業者がある**（クラウド・DB系に多い）。**対象APIごとにToSのベンチマーク条項を確認すること。** これは1位より確実な弱点。

## 【3位】Dockerコンテナ配布によるユーザーホスト型プローブ網（Globalping型を自前で持つ）

**構成**: D-1（月$3）の自前拠点をシードにし、**「Dockerを1つ動かすだけ」のプローブを配布**。ホストには「自分の拠点からの計測結果へのフルアクセス + サービス上位機能」を対価として渡す（FlightRadar24のBusinessサブスク方式）。

**なぜ3位か（=なぜ1位でないか）**:
- **成功したときの上限は最も高い。** FlightRadar24は5万受信機、PurpleAirは3万センサーで、いずれも自前網が事業の堀そのものになった。**追いつかれない。**
- **金銭コストが最も低い。** ハードを配らない・売らない。Dockerだけ。**ソロが唯一実行可能なユーザーホスト型の形。**
- **しかし鶏卵問題が最大。** フォロワーゼロで「Dockerを動かしてください」は誰も聞かない。**「先に価値のあるものを1人で出す」ことが前提条件**であり、それが1位・2位である。

→ **正しい順序: 1位または2位で「まず自分1人でデータを作り、公開して価値を証明する」→ そこに集まった人にプローブをホストしてもらう（3位に移行）。3位から始めることはできない。**
