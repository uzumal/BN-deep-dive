## 1. 結論

**コスト懸念は正当だった。しかし調べた結果、コストは制約ではなかった。**

ポインタ型は確かに月$1〜5で回る。だがその安さは3つの代償を伴い、そのうち2つは致命的である。

1. **安い＝参入障壁ゼロ＝既に全員が入っている**（飽和）
2. **YouTube規約が収益化を明文で禁止している**（コストがゼロでも収入もゼロに縛られる）
3. データ保持30日の上限により、過去12ラウンドで唯一の堀と判定された「時系列の蓄積」が規約で封じられている

そして**不動産をポインタ型に作り替えても、削減額は1万件規模で月91円**。コストは元々問題ではなく、問題はデータ入手経路だった（第13ラウンドの結論）。

## 2. ポインタ型の限界（一次ソース確認）

### 2-1. YouTubeの発見は無料枠で物理的に回らない
- `search.list` = 100 units、無料枠 10,000/日 → **1日100回が上限**
- 地理探索は半径1,000km上限。陸地1.49億km² ÷ 314万km² = 最低47回、実務150〜300回 → **全球1スイープ = 15,000〜30,000 units = 1.5〜3日分**
- **1日1回の全球スイープすら不可能**（ライブ配信の寿命は数時間なのに）
- `videos.list` は50件/1unit なので、**既知の数百〜2,000本を5〜15分間隔で生死確認する用途なら成立**する。worldwatcher.live が "hundreds" 規模なのは能力ではなく設計上限
- 増枠申請は "API Compliance Audit" を伴い、数週間〜数カ月（5カ月事例あり）。一括データ収集に見える用途は頻繁に却下。**「90日非アクティブでクォータ剥奪」条項も原文にある**

対照的に **Twitch は同時配信9.3〜9.7万chを約1.2分で全球スイープでき制限に余裕がある**が、位置情報を持たない。**Radio Browser API はキー不要・CORS可でブラウザ直叩き可**＝ポインタ型の理想形。

### 2-2. 規約が収益化を塞いでいる（YouTube Developer Terms 原文）
- 広告: 「YouTube API Dataを含むページでの広告販売は、**API Dataを取り除いても広告を正当化できる独立した価値**が同ページにない限り禁止」
- **「API Clients must not charge users to watch content in an embedded YouTube player.」**（サブスク不可）
- **「Non-Authorized Data は30日を超えて保持不可」**（時系列の堀を規約で封殺）
- プレーヤ最小200×200px、**1ページに自動再生プレーヤは1つまで**（"live wall" UIは不可）

→ ストリーム発見マップは「API Dataを抜いたら何も残らない」構造なので、**広告も課金も原則アウト**。

### 2-3. 埋め込みは壊れるのが定常状態
- X-Frame-Options / frame-ancestors の障害は**サイレント**（DevToolsにしか出ない）
- 個別動画の `embeddable=false`（エラー101/150）で**ピンの一定割合が常に壊れている**
- **Facebook/Instagramは2020-10-24に実際に一方的にoEmbedを壊した**——「埋め込みは永続」は一度反証済み
- 依存リスクの年表: FB/IG oEmbed(2020-10) → Heroku(2022-11) → Twitter(2023-02、**予告7日**) → Reddit・Apollo(2023-06) → Railway(2023-08) → Google Maps(2025-03) → **Netlify(2026-04)**。**平均年1.5回、どこかが条件を変えている**

### 2-4. ホットリンクの法的位置づけ
- 米: Perfect 10 v. Amazon の server test は**第9巡回区限定**（区外の地裁に否定例）
- EU: **C-392/19 VG Bild-Kunst** — 技術的措置を回避すれば公衆送信侵害
- 日本: **リーチサイト規制**（著113条2〜4項、2020-10-01施行）でリンク集約が射程。加えて**最判令2.7.21（リツイート事件）で自動トリミングが氏名表示権侵害**——**地図のサムネイル枠に合わせた自動クロップがまさにこの構図**

## 3. 飽和の実態（ポインタ型は「安い」が「空いていない」）

**最重要発見: overwatch.earth が既に存在する。** 32レイヤのライブ・グローバルデータを1つの3D地球儀に載せており、本調査の候補リストのうち**13項目が実装済み**（海底ケーブル、Cloudflare Radarのインターネット障害、PeeringDBのデータセンター/IX、BGP経路事故、Wikipediaライブ編集、公開ウェブカメラ、iNaturalist、航空機、船舶、衛星、FIRMS、Blitzortung、OpenAQ）。同種の集約グローブに God's Eye View（OSS）、World Monitor。

カテゴリ別の飽和: ライブカメラ地図 **英語圏12製品＋日本語圏5製品**、ラジオ地球儀6、traceroute可視化7、GeoGuessr代替12。

### 無料APIの罠
- **IT系ほど非商用（NC）条項が多い**: Cloudflare Radar は CC BY-NC 4.0、海底ケーブル(TeleGeography) は CC BY-NC-SA 3.0、Blitzortung は商用利用を明文禁止、Global Fishing Watch も非商用限定
- **実装不能なほど狭い枠**: Bitnodes 匿名1日10リクエスト、WiGLE 新規1日5クエリ、Windy Webcams 500 req/日＋画像URLが10分で失効
- **aprs.fi は規約で「同機能の別サイトへの全データコピー」を明示禁止**（地図サービス自体が違反になりうる）
- 唯一「imgタグでの画像利用」が明文許諾なのは **Booking.com Demand API**（第13ラウンドの結論と一致）
- ライセンスが最も自由: Safecast(CC0) / Met Museum(CC0画像40.6万点) / Foursquare OS Places(Apache 2.0, 1億POI) / adsb.lol(ODbL) / 米政府データ

### 構造的結論
> **lucent.earth が成立したのは安さではなく「まだカテゴリ名がなかったIRL配信を最初に地図に載せた」タイミング。構造は真似できてもタイミングは真似できない。**

なお lucent.earth 自体はレビューでコンテンツの質に否定的な評価（「配信者が例外なく退屈」）を受けており、収益化・作者・スタックは確認できなかった。

## 4. 25事例の結論 — 「載せるだけ」で育った例はゼロ

育った例は全て途中で構造が変質している:
- **(a) 自分でデータを集める網を持った**: FlightRadar24（受信機5万局）、MarineTraffic、PurpleAir、Numbeo
- **(b) 履歴を貯めて過去を売った**
- **(c) 特定業界のプロの業務に入った**
- **(d)「見る」を「知らせる」に変えた**: Flighty、Watch Duty

### 決定的な反例: earth.nullschool.net
東京在住の個人開発、13年継続、教科書・博物館・ドキュメンタリーに引用される世界的知名度。**それでも収益は寄付のみ、法人の従業員1名、本人が「趣味」と明言。**

### 「フォロワーゼロから」の例は見つからなかった
初期集客は例外なく: ニュース事件（FR24=火山噴火で1日400万訪問／Watch Duty=山火事）、既存の別トラフィック（FR24=航空券比較サイト／Ventusky=創業者が14歳から運営していたチェコ最大級の気象ポータル）、資本・公的資金（Windy=Seznam創業者／Radio Garden=EU研究資金／Watch Duty=自己資金$1M）、ストアのキュレーション（Flighty=Editor's Choice）。最も近いのが Numbeo（元Googleエンジニアが個人で、10年かけて3人規模）。

### 評価軸の修正提案（本ラウンド最大の示唆）
> **修正すべきは「母数が大きいこと」を重視する方針のほう。** Zoom Earth 1,100万訪問/月・MyRadar DL数千万で直近月$4万に対し、**Flighty はユーザー数が桁違いに小さいのに年$6M規模。ARPUが3桁違う。** 軸は母数ではなく「1人あたり払う理由」に移すべき。

ただし救いのある区別がある: **「眺め見型」と「監視型」は分けるべき**で、ユーザーが**自分の対象**（自分の便・自分の街の火事・自分が狙っている物件）を継続追跡する形なら、通知が作れてサブスクが成立する。

### 収益化の序列（ソロ・フォロワーゼロ）
API/データ販売 > 監視・通知サブスク（実売価は年$10〜60）> 履歴課金 > 受注への転換 > ハード販売 >> 寄付 >>> **広告（最下位。地図は帯域コストがトラフィックに比例するので特に相性が悪い）**

## 5. 不動産×ポインタ型の判定 — 不成立

| 規模 | R13キャッシュ配信 | リンクアウトのみ | 削減 |
|---|---|---|---|
| S（1万件） | $22.64 | **$22.07** | **月$0.57（¥91）／2.5%** |
| M（10万件） | $132.18 | $105.86 | 月$26 |
| L（100万件） | $340.13 | $215.01 | 月$125（37%） |

**ホットリンクの月額はリンクアウトと完全に同一**（差はUXと法的リスクのみ）。残る$215は全部「データを持つコスト」であって画像コストではない。

「自分でホストせず室内写真」の手段は**実質存在しない**: リンクアウト（Zillow ToUが不動産事業者以外からのリンクを制限）／OGP（取得＝スクレイピングで入口違反）／**oEmbed（`iamcal/oembed` に Zillow/Rightmove/SUUMO 等は0件）**／iframe（frame-ancestors）／提携（それは提携型であってポインタ型ではない）。

**結論: コストは元々問題ではなかった。削減額が月91円である以上、コストを理由に不動産案を変形する意味はない。**

## 6. ゼロ円構成（作るなら、これが最善形）

**GitHub Actions（publicリポジトリ＝分数無制限）で cron 収集 → JSONをコミット → Cloudflare Pages（静的アセットは帯域・リクエスト無制限で無料、一次確認）で配信 → iframe再生（動画帯域は相手持ち）**
= **月$1〜5（ドメイン代のみ）**

守る線6つ:
1. APIをクライアントから叩かない（`videos.list`で1万人、`search.list`で**100人**で枯れる）
2. Worker/Functionsを1つも挟まない（10万req/日の壁）
3. Pagesビルドは月500回≒90分間隔（速い更新は Worker cron→R2直配信で$0）
4. KVは書込1,000/日
5. Cron Triggersは5個
6. YouTube由来データは30日以内に削除/更新

参考: **Netlify Free は2026-04-14に実質15GB/月へ縮小 → 約6,000人で停止**、Vercel Hobbyは100GBで停止（Proの実例で$1,141）。**Cloudflare Pages静的は$0**。

## 7. 残った選択肢（トリレンマ）

| 道 | コスト | 堀 | 収益 | 障害 |
|---|---|---|---|---|
| **A. ポインタ型マップ** | 月$1〜5 | **なし**（規約が30日で消させる） | **規約で禁止** | 飽和＋タイミングは再現不能 |
| **B. 不動産×提携（Kyero XML）** | 月$22 | エージェント関係＋掲載履歴 | 掲載課金/アフィリ/ニュースレター | 営業6ヶ月 |
| **C. 自前データ×監視型** | 中 | **時系列・実測（12ラウンドの結論）** | 通知サブスク（ARPUが3桁高い） | 収集の手間 |

**一般原則（本ラウンドの最重要文）**
> ポインタ型の成否は「元プラットフォームがあなたを**送客**とみなすか**収奪**とみなすか」で決まり、**その判定権を他人に渡すのがポインタ型を選ぶということ**である。
